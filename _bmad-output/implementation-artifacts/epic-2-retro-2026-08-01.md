## 2. 잘된 점 (Wins)

- Epic 2 전체에서 `Capability.BOM`, `Capability.PRODUCT_MATERIAL` 게이트 일관 적용

- **자산**: 다음 epic planning에서 "이 capability가 필요한가?" 체크리스트로 활용

### W2. Audit-first + idempotent no-op (CR 1.1 lesson) 전사 확산
- 2-1 / 2-3 모두 `body.model_dump(exclude_unset=True)` + `changed_fields` 빈 경우 audit skip
- 2-3 AC #9에서 same-type no-op은 BOM count까지 early-return (2중 최적화)
- **자산**: 모든 CRUD write path의 표준 패턴

### W3. bulk-replace PUT 100% invariant (CR 2.1 lesson 직접 반영)
- 2-2 BOM 매트릭스에서 100% invariant를 atomic transaction으로 강제
- 사후 발견이 아닌 사전 차단 → AC 위반이 발생할 수 없는 구조
- **자산**: Epic 4 calculation engine (F3.x 단일 진입), Epic 5 inventory_ledger append-only-leaning에도 같은 패턴

### W4. cross-language drift test의 regex parsing 채택
- TS mirror를 regex로 파싱해 Python enum과 비교 (Story 2.1)
- strict 정적 import보다 견고 (TS는 진실의 원천이 아님, Python enum이 truth source)
- **자산**: Epic 3 이후 모든 enum 추가 시 동일한 테스트 패턴

### W5. Story 2.3 review의 TOCTOU 방지 (D2 patch)

## 4. 핵심 인사이트 (Top Lessons)

### L1. "capability × type matrix"는 Epic 2의 자산, Epic 3~9의 표준 패턴
- 모든 신규 모듈(m2_input, m3_calculate, m4_inventory...)에서 같은 frozenset + `is_X_allowed_for_industry` 패턴 적용 예정
- 문서화 권장: `docs/capability-matrix.md` (Action Item A3)

### L2. "사전 차단(atomic PUT) > 사후 발견"
- 2-2 BOM 100% invariant의 atomic bulk-replace는 Epic 4 calculation engine, Epic 5 inventory append-only에서도 반복될 핵심 패턴
- "100% invariant"를 강제하는 write path는 항상 bulk-replace로 설계

### L3. plumbing 격차는 가속화 가능, 인선이 누적되면 리팩터 비용이 선형보다 빠르게 증가

- Epic 3 첫 스토리 전에 한 번 더 우선순위 재평가 필요 (Action Item A4)
