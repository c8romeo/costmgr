## Verdict

**has-gaps** — the spine is a structurally sound substrate: the 15 inherited core ADs (AD-1…AD-15) are enforced, the 10 cross-module ADs added in the 2026-07-24 round (AD-16…AD-25) close the most exploitable divergence surfaces the adversary review surfaced, the stack is pinned to web-verified versions, and the operational envelope is on the page. It is downstream-consumable for the modules M0–M12 with two exceptions: (i) AD-9's "no tenant caching on Vercel / no cross-region replication" is asserted as Rule without a named enforcement surface, and (ii) several dimensions the altitude owns are decided at the spine level but not at the lint level — meaning two builders can each obey AD-9, AD-23, AD-25 to the letter and still diverge on the operational envelope, the settings-version migration, and the LISTEN/NOTIFY plumbing. The Deferred section is honest but the AD-26…AD-35 candidates carry real divergence risk that "before Implementation Readiness" is a soft deadline the team has historically slipped.

## Divergences Found (tiered)

### Critical

- **[c1] AD-9 enforcement surface is asserted, not named.** "`Vercel may cache static assets globally but never tenant data`" and "`Cross-region DB replication is disabled`" are written as Rules, but the spine names no enforcement surface — no CI lint that scans route handlers for `Cache-Control: public` on tenant responses, no Supabase read-replica audit, no runtime check. **Failure scenario:** an M5 report PDF endpoint is built with `Cache-Control: s-maxage=86400, stale-while-revalidate=31536000` (a perfectly normal Vercel pattern for "fast") and routes through the Vercel edge. The report contains tenant financial data. Vercel's edge now holds the response globally for 31 days. Each obeys AD-9 ("Vercel may cache static assets globally but never tenant data"). The PRD §13.2 "월 인프라 예산 10만원" constraint rules out Vercel Enterprise's per-region cache controls, so the enforcement must be at the route layer. Likewise, a Supabase operator enables a read replica in `ap-northeast-1` (Tokyo) for performance; tenant replication is now on. Each obeys AD-9. **Fix:** append to AD-9 either a lint rule name (e.g., "no `Cache-Control: public` in CI grep over `apps/api/` routes that touch `tenant_id`") or a runtime check (e.g., "API gateway strips `Cache-Control` on responses where `body.tenant_id` is non-null"). The "cross-region replication" half needs a Supabase project-config assertion, not a doc note.

### High

- **[h1] AD-9 "no tenant payload logging on Railway" lacks a runtime filter.** The Rule says "`tenant payload logging, persistent disk writes, response caching, and backups on Railway are forbidden`." The convention says logging uses structlog JSON with `trace_id`. The enforcement surface for "no tenant payload in logs" is not named. **Failure scenario:** an M11 reversal handler logs `{"event":"reversal", "tenant_id": "...", "amount": 12345678, "line_items": ...}` for debugging. structlog writes JSON to stdout; Railway collects stdout. Even with trace_id, the payload is in Railway's log infra. PIPA audit (deferred OK) flags this. A second engineer builds a `redact_tenant_payload` middleware that runs before structlog. Three engineers, three opinions, no lint rule. **Fix:** add to AD-9: "`structlog processors include a redact_processor that strips any field whose name matches `*tenant*` or `*amount*` from any log emitted by adapters on the Railway runtime. CI test asserts a sample reversal payload produces no amount/tenant_id keys in the rendered log line.`"

- **[h2] AD-23 "settings_version" gating mechanism is not specified.** The Rule says "`Each module writes only its namespace through a version-checked settings service. The settings_version column gates which module's writes are accepted.`" Postgres column-level check constraint? ORM-level optimistic concurrency? App-level read-modify-write lock? None of these is named. **Failure scenario:** M0's engineer writes the settings service with `UPDATE tenant_settings SET settings = settings || $1::jsonb, settings_version = settings_version + 1 WHERE tenant_id = $2` (last-write-wins). M1's engineer writes a row-level optimistic version `WHERE tenant_id = $2 AND settings_version = $3`. M0's onboarding save at the same time as M1's allocation-method change: M0 sees stale `settings_version`, updates `settings_version=4`, M1's update then writes `settings_version=4` against `settings_version=3` (its read). Last write wins, M0's namespace is overwritten. Each obeys AD-23. **Fix:** name the mechanism — "settings_version is updated via Postgres `xmin` style OCC; the settings service is the only writer; concurrent writes raise `CONCURRENT_SETTINGS_WRITE` and the UI re-reads + retries." Or add an AD-23a sentence saying "the writer is enforced by a `BEFORE UPDATE` trigger that rejects writes where `settings_version` is not equal to the value the client just read."

- **[h3] AD-25 LISTEN/NOTIFY via Supabase connection pooler is plausibly broken.** The Rule says "`A new AD-4 commit, an AD-22 reversal insert, or an M11 reopen emits one DB notification; the M10 adapter consumes it.`" Supabase's pooling uses PgBouncer in transaction mode by default — `LISTEN` works only in session mode. **Failure scenario:** M10's adapter opens a connection through PgBouncer, calls `LISTEN result_invalidation`, processes a request, PgBouncer ends the transaction and recycles the connection. The notification is missed. M10's insight cache now serves stale insights for the next calculation. Each obeys AD-25. **Fix:** add to AD-25: "`M10 consumes notifications via a dedicated session-mode connection that bypasses PgBouncer (Supabase `direct connection` string). The connection ID is logged at startup so the operator can verify it is not pooled.`" If session mode is unavailable through Supabase, AD-25 needs an alternative (polling `fiscal_period_snapshots.last_modified` with a debounce — explicitly named, not "the M10 adapter consumes it").

- **[h4] Spec coverage gap: M7 (시뮬레이션) and M12 (계정·운영) backup policy are not governed by any AD.** The capability map binds M7 to AD-5 only and M12 to AD-3 + AD-10 only. PRD §8.1 M7(a) requires "BEP 수량·목표 이익을 1초 이내로 재계산" (latency/SLA) and M7(b) requires "차입금·이자율·상승률·세율 4종 파라미터의 사용자 입력을 강제" (validation contract). PRD §8.1 M12(b) requires "일 1회 자동 백업 + 셀프 다운로드(JSON)". **Failure scenario:** M7's engineer builds a slider that calls `engine.calculate` per change (≥2s cold path, ~500ms warm). PRD's 1초 target is missed in production. A second engineer pre-computes `manufacturing_cost` per product and runs BEP in JS — passes latency, but the engine result is fresh-of-date and ignores post-1차 M5 changes. Two implementations, two failure modes, each obeys AD-5. M12's backup engineer uses a Vercel cron for daily JSON; the second uses a Supabase scheduled function. The output format diverges. **Fix:** add an AD-26 (or extend AD-23 / AD-12) that pins the M7 input contract (4 params) and the latency budget, and an AD-27 (or extend AD-3) that pins the M12 backup shape as JSON-only with a documented schema.

- **[h5] AD-7 "denied and counted" has no count shape.** The Rule says "`Attempts by M10 to write confirmed-input tables are denied and counted; target is zero.`" Where is the count? `audit_logs`? A separate `m10_guardrail_counters` table? `structlog`? **Failure scenario:** M10's engineer writes a deny-log to `audit_logs` with `event_type='m10_write_denied'`. M3's monitoring queries `audit_logs` for the violation. A second migration drops the `event_type` enum to clean up. The count goes silent. The "target is zero" commitment becomes unverifiable. SM-3a "계산 결과 변경 시도 = 0건" can't be measured. **Fix:** add to AD-7: "`denied-write attempts are recorded in a dedicated `ai_guardrail_counters` table with `(tenant_id, attempted_by, forbidden_table, attempt_count, last_attempt_at)`. The view is namespaced so M10 cannot write to it. SM-3a reads from this table.`"

### Medium

- **[m1] AD-11 import-linter rule is not named.** The mermaid diagram is in the spine, but the actual lint rule (e.g., `import-linter` configuration forbidding `packages/cost_engine` from importing `apps/api`, `sqlalchemy`, `httpx`, `pydantic.BaseModel` from outside `packages/cost_engine/dto`) is not in the spine. **Failure scenario:** an M7 engineer adds a `from ...adapters.db import Session` in `packages/cost_engine/core/calculations.py` to short-circuit a call. Import linter is not configured, so the lint passes. The engine is now coupled to DB. Each obeys AD-1, AD-5. **Fix:** add to AD-11 "`the import-linter config lives at `packages/cost_engine/.importlinter` and is enforced in CI; contracts: engines-forbidden = {*sqlalchemy*, *httpx*, *pydantic.BaseModel*}; adapters-forbidden = {*packages.cost_engine.core*}.`"

- **[m2] AD-14 "unmanaged components that violate the 1-operator constraint" is vague.** "1-operator constraint" is repeated but not measured. The spine bans Celery, Kafka, Redis-as-persistent-queue explicitly; everything else is judgment. **Failure scenario:** M10's engineer adds BullMQ for AI insight queueing (Redis). Redis is already present for Supabase session storage — borderline. The second engineer proposes Temporal for the M11 reversal flow. The third proposes a self-hosted Meilisearch. All three are "managed" in the loose sense, but each adds operator burden. No ruling. **Fix:** add a one-line criterion to AD-14: "`managed = provider runs the control plane; the operator only configures via dashboard or API; same observability contract as the rest of the stack.`"

- **[m3] AD-16 "M3 is the only writer" + AD-22 "M11 writes reversal" is precise but the snapshot's `state` enum needs an explicit `reversed` value in the schema.** AD-20 says `state ∈ {'draft','verified','committed','reversed'}` is the lifecycle. AD-16 names the snapshot columns. AD-22 says "reversal is represented by an append-only AD-22 event and never by mutating the committed row." That leaves the snapshot's `state` field ambiguous: does it transition to `reversed` on a reversal event, or does the snapshot retain `state='committed'` and the reversal row lives in `inventory_ledger` only? **Failure scenario:** M5's report joins `fiscal_period_snapshots WHERE state='committed'` (correct) and also tries to filter by `state='reversed'` (probably wrong). M11's engineer writes the snapshot's `state` to `reversed` on reversal. M5's report hides the row. Each obeys AD-16, AD-20, AD-22. **Fix:** clarify in AD-20 / AD-22: "`fiscal_period_snapshots.state` does NOT transition to `reversed`; the snapshot remains `committed` permanently. Reversal is reflected in a derived `fiscal_period_snapshots.is_reversed` boolean computed by joining the latest `inventory_ledger` reversal row per `tenant_id`, period_key, product_id`."

- **[m4] AD-19 "Service-only tenants use the same endpoint with only the applicable ABC path" — what about the ABC path for ② tenants?** The Rule says "`Service-only tenants use the same endpoint with only the applicable ABC path.`" The endpoint is `POST /api/v1/calc` owned by M3. AD-21 says M9 owns `CCRPort.compute`. So M3 must call M9's port for an ② tenant. AD-19 says M9 exposes no public endpoint. So M3 is the only public surface. **Failure scenario:** operator upgrades a ② tenant to ③ (now manufactures + service). The endpoint must switch from "ABC only" to "merged traditional + ABC." M3's engineer forgets to handle the upgrade flag; M9's engineer assumes M3 will route. Result: ③ tenant's first calculation runs only the ABC path (missing traditional costing). Each obeys AD-19, AD-21. **Fix:** add a sentence to AD-19: "`M3's orchestrator dispatches by tenant kind on every call; ② tenants route to M9's port only; ③·④ tenants route to both M3's traditional ports and M9's ABC port; the orchestrator re-routes on tenant-kind change without a state migration.`"

- **[m5] AD-26 candidate "`split source from is_estimated`" carries divergence risk that is acknowledged Deferred.** The Deferred section names this as "AD-26: split `source` from `is_estimated`" — but the spine doesn't carry an AD-26 stub that defines the split. **Failure scenario:** M2's engineer adds `source` enum `'manual' | 'excel' | 'ai_extracted' | 'ai_insight'` and keeps `is_estimated` as a separate boolean. M3's engineer reads only `source` (treats `ai_extracted` as draft-only via AD-7) and ignores `is_estimated`. M5's engineer displays `is_estimated=true` badge regardless of source. M2's "is_estimated" input is now silently included in M3 calculations from Excel uploads (which M5 badges as estimated but M3 doesn't gate). Each obeys AD-7, AD-13. **Fix:** promote AD-26 from Deferred to a stub AD with a Rule: "`source` and `is_estimated` are independent fields; M3's engine gate reads `source` only; M5's UI reads `is_estimated` only; the AD-17 promotion port enriches both.`"

- **[m6] AD-15 "Period keys follow AD-24" — the convention table says "Dates and periods" but the row references AD-15·AD-24 where AD-15 doesn't itself define period nomenclature.** The convention table is a summary convenience; the canonical authority is AD-24. Cosmetic, but two engineers could read the table and disagree on which row owns period key typing. **Fix:** add a footnote to the convention table: "`period keys: AD-24 is the canonical source; this row is a pointer.`"

- **[m7] AD-9 "PIPA cross-border processing notice and consent" is Deferred-to-pilot.** The Rule says "`Before pilot launch, the operator must complete PIPA cross-border processing notice/consent and processor-contract review.`" This is a go-live gate, not a structural rule. Two engineers can each build the M5 report PDF endpoint and a tenant who uploads a financial statement, and the deployment proceeds without the legal review. **Failure scenario:** M10's document extraction sends a tenant's financial PDF to Claude API (Anthropic Inc. USA). Railway Singapore compute processes tenant payloads (Singapore). Supabase stores data (Seoul). The cross-border processing chain is real but the PIPA notice hasn't been drafted. Pilot launch occurs. **Fix:** add the legal review as a CI gate or a deployment-blocker in AD-9: "`ci-deploy-pilot fails unless env var PIPA_PILOT_REVIEW_COMPLETED_AT is set and within 30 days of TODAY.`"

- **[m8] AD-25 DB notification payload schema is not named.** AD-25 says "`A new AD-4 commit, an AD-22 reversal insert, or an M11 reopen emits one DB notification.`" The notification channel name and JSON payload are not specified. **Failure scenario:** M3's engineer uses `NOTIFY result_invalidation, '{"period_key":"2026-07"}'`. M11's engineer uses `NOTIFY result_invalidation, '{"tenant_id":"...", "period_key":"..."}'`. M10's adapter subscribes to the channel and expects both. M3's notification does not include `tenant_id`. M10's adapter can't invalidate per tenant. Each obeys AD-25. **Fix:** add to AD-25: "`channel name = `result_invalidation`; payload = `{\"tenant_id\": UUID, \"period_key\": TEXT, \"reason\": \"commit|reversal|reopen\", \"result_hash\": TEXT}`. M10 rejects notifications whose payload does not parse.`"

- **[m9] M12 2FA enforcement vs M0 onboarding ordering.** AD-10 requires 2FA. PRD §8.1 M12(a) says "2FA 미설정 상태에서 M2 진입을 차단." M2's engineer hard-blocks on `tenants.2fa_enabled=false`. M0's engineer considers 2FA setup as part of M0 (post-registration). The Gate between M0-complete and M2-allowed is not a single AD. **Failure scenario:** M0's engineer ships a "skip 2FA for now" affordance for the demo flow. M2's check passes (2FA is enabled). M12's check fails (2FA setup never completed). The user is in M2 but M12's audit shows the 2FA setup was never confirmed. **Fix:** add to AD-10: "`M2's entry guard is on `tenant_users.totp_verified_at IS NOT NULL`, not on `tenants.2fa_enabled`. M0's onboarding must surface the 2FA setup screen before any other M0 step. AD-10 owns the gate.`"

- **[m10] AD-16 "deterministic `result_hash`" — the hash input is not specified.** The Rule says "`plus deterministic result_hash`" but the canonical input set (just the cost columns? + `tenant_id` + `period_key`?) is missing. **Failure scenario:** M3's engineer hashes the 6 normalized columns only. M5's engineer hashes the same 6 columns plus `tenant_id` and `period_key` (since the cache is keyed on those). M11's engineer hashes the 6 columns plus segment and engine_type. M10's cache (AD-25) keys on `(tenant_id, period_key, result_hash)` — three different hashes for the same logical result. **Fix:** add to AD-16: "`result_hash = sha256(tenant_id || period_key || segment_id || engine_type || material_cost || labor_cost || overhead_cost || manufacturing_cost || inventory_adjustment)`. Expressed as a Python string concat on the canonical string forms of Decimal values (no float conversion).`"

### Low

- **[l1] AD-19 service-only tenant path doesn't say how M3 dispatches to M9.** The Rule names "POST /api/v1/calc" owned by M3 and "M9 exposes no separate public calculation endpoint" but the internal dispatch (M3 → M9 port) is implicit. Two engineers can build M3's orchestrator with M9's port as a hard-import or a service locator. Cosmetic but worth nailing. (already covered by h4-but-m4 also.)

- **[l2] AD-9 "Cross-region DB replication is disabled" — Supabase's read replicas are in-region only by default; the rule might be a no-op.** Worth flagging as observation: if Supabase already doesn't cross-region-replicate by default, the rule is documentation. If Supabase does enable cross-region on paid tiers, the rule needs a config assertion. (covered by c1.)

- **[l3] AD-14 "Banned infrastructure" enumeration: Celery, Kafka, Redis-as-persistent-queue.** The list is illustrative but not exhaustive. A new vector (e.g., Sidekiq, RabbitMQ) is not pre-banned. Low impact because the rule "and unmanaged components that violate the 1-operator constraint" is the catch-all. (covered by m2.)

- **[l4] AD-15 "IDs are UUID v7; tenant_id is ULID."** UUID v7 is not yet a stable Postgres type (Postgres 17 has `uuidv7()` in some extensions but not core). The spine specifies `UUID v7` without a generation source. **Failure scenario:** M1's engineer uses `uuid_generate_v7()` from a Postgres extension; M2's engineer uses Python's `uuid.uuid7()` (Python 3.14+). One path produces a v7 UUID, the other may produce a v4 if Python is older. **Fix:** add: "`UUID v7 is generated by Python `uuid.uuid7()` (Python 3.14+) for client-side IDs or Postgres `pg_uuidv7` extension for server-side. Migration adds the extension.`"

- **[l5] AD-25 `result_hash` collision probability is not bounded.** With 32-byte SHA-256, collision is practically zero, but the Rule says "deterministic" without naming the algorithm. A minor upgrade could swap to a different hash. **Fix:** "`result_hash algorithm = SHA-256, hex-encoded lowercase. Any change to the algorithm is a major-version bump in `cost_engine`.`"

- **[l6] M7 simulation measurable outcome under AD-5.** The PRD §8.1 M7(a) commits "1초 이내" recompute. AD-5 commits purity. The latency budget is not architecturally enforced. The 1초 is a UX constraint, not a structural AD. (already covered by h4.)

- **[l7] Operational envelope notes paragraph (§)"Connection pooling is revisited when concurrent tenants exceed 20."** The number 20 is asserted without measurement methodology. **Fix:** add the baseline (current Supabase pool default, Supabase plan tier) and the measurement path (operator console graph of `pg_stat_activity` count).

- **[l8] AD-22 "M4 calls request_reversal" — what about M0/M1/M2 corrections to OPEN periods (not closed)?** AD-6 says closed periods reject business-data INSERTs except AD-22 reversal; AD-22 says M4 calls request_reversal. Open periods allow direct edits per the PRD §8.1 M4(a) "기초재고 입력 후 자동 이월 체인 개시, 이후 수동 입력은 차단." This is post-기초 phase. **Failure scenario:** M2's engineer writes a direct UPDATE on `monthly_inputs` for an open period (legal per AD-6) but skips the audit log because open periods are not under the reversal regime. Auditors can't distinguish "operator correction" from "user correction." Cosmetic, but the audit story holds only for closed periods per the current spine. **Fix:** add to AD-2 / AD-22: "`audit_logs captures every write to `monthly_inputs`, `inventory_ledger`, and `fiscal_period_snapshots` regardless of period status. The `action` enum distinguishes `correction_open` (legal direct update) from `reversal_closed` (AD-22 reversal).`"

- **[l9] AD-20 "verified results may be previewed with PREVIEW labeling" — the preview port is implicit.** Adversary review's AD-29 candidate ("separate non-authoritative preview port") is still Deferred. If M5 ships a preview endpoint now, it will likely re-use the M11 read port, which serves `committed` rows. The conflict is "preview" vs "committed" access. Per l1/h4, the preview path is a team-divergence risk. Already covered by Deferred AD-29.

- **[l10] Operational envelope diagram lists "GitHub" as the deploy source but AD-3 RLS does not mention CI's service-role requirements.** If a CI test runs `service_role` bypass without an audit row, AD-3's Rule is violated. **Fix:** add: "`CI pipeline uses `service_role` only in dev-tenant scope; production CI uses anonymous + seeded test users; any `service_role` write in CI inserts into `audit_logs` with `actor='ci-runner'` and `reason='test-only'`."`

## Summary

The spine is **downstream-usable** for M0–M12 implementation with two structural caveats (c1, h4) and four operational caveats (h1, h2, h3, h5). The Good-spine checklist passes on 6 of 8 axes: (a) divergence-point coverage is broad but the AD-26 candidates are still deferred; (b) every AD's Rule is enforceable in principle but 7 of 25 Rules (c1, h1, h2, h3, h5, m1, m8) lack a named enforcement surface; (c) Deferred items are tracked; (d) named tech is verified-current; (e) no brownfield to ratify; (f) PRD capability coverage is complete modulo M7 latency and M12 backup; (g) no parent spine; (h) operational envelope is decided.

The top three findings to clear before Implementation Readiness:

1. **c1 + h1 + l10 — AD-9 needs an enforcement surface for Vercel cache, Railway log redaction, and DB replication.** Without these, the residency rule is a doc note, not a structural rule.
2. **h4 — M7 latency and M12 backup need explicit ADs.** The capability map binds these modules to a single AD each; PRD §8.1 acceptance criteria are not architecturally pinned.
3. **h5 + m5 + m8 — AD-7 count shape, AD-26 source-vs-estimated split, AD-25 notification payload.** Each is a 5-minute fix in the spine text but a 5-day fix in the codebase if the team diverges first.
