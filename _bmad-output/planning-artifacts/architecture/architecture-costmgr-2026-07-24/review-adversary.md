# Architecture Spine — Adversary Review

- **Spine under review:** `architecture/architecture-costmgr-2026-07-24/ARCHITECTURE-SPINE.md`
- **Driving PRD:** `_bmad-output/planning-artifacts/prd.md` (v2.0, 2026-07-24)
- **Paradigm:** Modular Monolith + Hexagonal Core (AD-1), 15 ADs.
- **Lens:** construct two units one level down that each obey every AD to the letter yet still build incompatibly.

## Verdict

**has-gaps** — 15 ADs close a real surface (engine purity, RLS, append-only ledger, money, residency, dependency direction), but a meaningful class of cross-module *shared data shapes* and *shared state machines* is not pinned by any AD. Two engineers building M3/M5/M11 snapshots, M9 CCR, M10→M3 promotion, M0/M1 settings, and the cross-engine [계산] order can each satisfy AD-1…AD-15 verbatim and still produce code that won't compile or reconcile against itself. The most dangerous gaps are at *write/ownership boundaries* (who writes the snapshot, who promotes an AI draft, who is allowed to close a period) and at *entity identity boundaries* (product across M1/M3/M4/M5/M9, department across M1/M3/M9).

## Divergences Found

- **[critical] Snapshot schema divergence (M3 ↔ M5 ↔ M11)** — AD-12 says "write `fiscal_period_snapshots` row" and AD-2 says reversal rows, but neither AD defines the row's shape (per-month key, per-fiscal-period key, per-snapshot-id, what columns are persisted vs recomputed from inputs, JSON envelope vs normalized columns). M3's engineer writes `{snapshot_id, fiscal_period, results_json}` keyed per `YYYY-MM`. M5's engineer assumes `(fiscal_period, segment_id, product_id)` normalized rows because reports aggregate across 12 months. M11's engineer assumes one row per period per tenant. Each obeys AD-2, AD-4, AD-6, AD-12. Result: M5 reads from M3's JSON and can't filter, M11 sees duplicate rows, V4 reconciliation references vanish. *Suggested AD-16 candidate:* "`fiscal_period_snapshots` is keyed on `(tenant_id, period_key, segment_id, engine_type)`; the row contains normalized columns for `material_cost`, `labor_cost`, `ohd_cost`, `manufacturing_cost`, `inventory_adjustment`, plus a deterministic `result_hash`. No JSON-blob output. M3 is the only writer; M5 and M11 are read-only consumers; mid-flight rows are written with `state='in_flight'` and atomically transitioned to `state='committed'` inside AD-4's transaction."

- **[critical] AI draft → confirmed input promotion (M0/M10 ↔ M2 ↔ M3)** — AD-7 says "AI outputs … are stored as `input_drafts` and never reach the engine path. The engine path reads only confirmed (user-approved) inputs." But no AD defines the *promotion*: which service moves a draft row to `monthly_inputs`, which endpoint exposes it, who is authorized, whether the draft is deleted on promote or kept for audit, what happens to the `confidence` and `is_estimated` flags, and whether partial promotion is allowed. M10's engineer builds `POST /drafts/{id}/confirm` that copies fields into `monthly_inputs` and deletes the draft. M2's engineer builds `PUT /monthly_inputs/{period}` that accepts a `draft_id` reference and inlines. M3's engine sees two different input shapes (copied row vs reference row). Each obeys AD-7. *Suggested AD-17 candidate:* "Promotion is a single engine port `InputPromoter.promote(tenant_id, period_key, draft_ids: list[UUID]) -> MonthlyInput` implemented only by the `db` adapter. M2 calls the port; M10 never writes to engine-path tables. Promotion is idempotent on `(tenant_id, period_key, source_draft_id)`, leaves the draft row in place with `state='promoted'` (append-only per AD-2), and writes an `audit_log` row with actor + draft hash. The engine port contract is the single point of truth for the `MonthlyInput` shape — M2 and M3 cannot redefine it."

- **[critical] Cost-object identity across engines (M1 ↔ M3 ↔ M4 ↔ M5 ↔ M9)** — ERD lists `ITEM` (M1) and `COST_ALLOCATION` / `SEGMENT_ALLOCATION`, but the spine never says whether the same product sold to a service customer (③ tenant) is one `item_id` or two (one in M1's traditional catalog, one in M9's cost-object catalog). M3's engineer uses the same `item_id` because A2's "제조원가/완전원가" view requires it. M9's engineer creates a parallel `cost_object_id` because ABC's activity-driver space is independent. M4's ledger writes reference the M1 item. M5's report joins on a field that one side calls `product_id` and the other calls `cost_object_id`. Each obeys AD-3, AD-8, AD-15. Result: ABC report totals never reconcile to traditional P&L for ③·④ tenants. *Suggested AD-18 candidate:* "A single entity `product` (renamed from `ITEM` in the ERD) with `product_id UUID` carries both traditional (`unit_cost`, `bom_id`) and ABC (`is_cost_object`, `default_activity_id`) attributes. The cost engine accepts a `product_id` and returns both `manufacturing_cost` (traditional) and `abc_cost` (if applicable) in the same result record. ABC never introduces a parallel identifier; it adds a `product_role` enum (`'trad_only' | 'abc_only' | 'both'`). M4's ledger and M5's reports join on `product_id` only."

- **[critical] Cross-engine [계산] order and ownership (M3 ↔ M9 ↔ M11)** — AD-12 pins M3's verification order (V1·V4·V7·V8) and AD-6 locks the close. But PRD §4.2 forces "부문분할 → 제조 원가계산 → ABC 계산 → 공동 마감" while PRD §8.1 gives M3 and M9 each their own [계산] acceptance criteria. The spine does not say whether there is one [계산] button (M3 orchestrates M9) or two buttons (M3 + M9, user must click in order). M3's engineer builds a single orchestrator that calls M9 internally. M9's engineer exposes its own `/abc/calculate` endpoint so ② tenants (service-only) can run it. M11's close assumes M9 has been called. A ③ tenant on M9's first cut never sees V1·V4·V7·V8 fire against the merged result. Each obeys AD-4, AD-7, AD-12. *Suggested AD-19 candidate:* "The [계산] entry point is `POST /api/calc` (M3) only. M3's orchestrator dispatches to M9's engine port `abc_calc.compute(period_key)` in a defined sub-step inside the same AD-4 transaction. M9's standalone `POST /api/abc/calculate` endpoint is allowed only for ② (service-only) tenants and is forbidden for ③·④; a tenant-upgrade flow migrates ABC state into M3's orchestration. UI shows one [계산] button per period; M9 has no UI button in ③·④ contexts."

- **[high] Snapshot lifecycle state machine (M3 ↔ M5 ↔ M11)** — AD-4 forbids exposing results before commit; AD-6 forbids post-close mutation; AD-12 ties verification to the same transaction. None of the three ADs names a `state` field on calculation results. M3's engineer writes only the committed snapshot. M5's engineer wants a "draft preview" so users can review before commit. M11's engineer wants an `is_locked` flag separate from `state`. Two engineers can each implement state semantics and find that M5's preview shows figures M11 hasn't yet locked, or that M3's audit log omits pre-commit attempts (SM-3a "계산 결과 변경 시도 = 0건" can't be measured). *Suggested AD-20 candidate:* "Every calculation result row carries `state ∈ {'draft','verified','committed','reversed'}` and `verification_status ∈ {'pending','passed','failed'}`. State transitions are: `draft → verified` (after V1·V4·V7·V8), `verified → committed` (after AD-4 commit, M11 close lock), `committed → reversed` (only via AD-2 reversal row). Only `verified` rows are visible to non-owner roles; only `committed` rows feed M5 reports. SM-3a counts every transition into and out of `state='draft'`."

- **[high] CCR computation disagreement (M9 ↔ M3)** — PRD §7.2 pins CCR at department level (AS-2), but the spine does not define what "부서 원가" includes. M3's engineer reads M9's CCR as "indirect costs allocated to department" (i.e., already-net of direct labor, because M3 writes `direct_labor_cost` to the same department). M9's engineer reads "부서 원가 = sum of accounts tagged to the department, gross". The two disagree on the denominator by the amount of direct labor. Each obeys AD-5 (purity), AD-7 (AI non-authoritative), AD-15 (naming). *Suggested AD-21 candidate:* "CCR is computed by the engine as `CCR = (department_indirect_cost) / (practical_capacity_hours)`, where `department_indirect_cost` is the engine's pre-allocation indirect total for the department (i.e., total department cost minus amounts already classified as `direct_labor` or `direct_material` by M1's account tags). The port signature `CCRPort.compute(tenant_id, period_key, department_id) -> Decimal` is the only definition; M3 reads CCR from this port and never recomputes it; M9's TDABC output is the writer."

- **[high] Reversal row construction (M4 ↔ M11)** — AD-2 says "reversal row INSERT + new row INSERT." It does not define the linkage (a `reverses_id` column, an `original_event_id`), the column semantics (sign-flip vs new pair), the agent (UI-driven operator action vs M11-driven close correction), or the idempotency guarantee. M4's engineer, seeing "기초재고 입력 후 자동 이월 체인 개시, 이후 수동 입력은 차단" (PRD §8.1 M4), builds a "manual correction" UI that writes a paired reversal+new row pair. M11's engineer builds an "unlock and re-close" flow that updates the original. Each obeys AD-2, AD-6. Result: two kinds of correction rows, no way to audit which is which. *Suggested AD-22 candidate:* "Every ledger row carries `reverses_event_id UUID NULL` and `reversal_of_period_key`. A reversal is always a single new row referencing the original via `reverses_event_id`; the original is never updated. M11's close correction path is the only authorized agent for ledger reversals; M4's UI exposes a `request_reversal(event_id, reason)` port that M11 fulfills. Idempotency: `reverses_event_id` is UNIQUE per `tenant_id`."

- **[high] Two `tenant_settings` tables (M0 ↔ M1 ↔ M9)** — Capability map shows M0 for "settings · AI extraction" and M1 for "baseline · items · BOM · accounts." No AD says whether these are one table or two. M0's engineer creates `tenant_settings` for currency, language, fiscal-year start, AI defaults (AD-7 storage). M1's engineer creates `tenant_baseline_settings` for allocation method (3종 택1), fixed/variable tags, BOM policy. M9's engineer creates `tenant_abc_settings` for `method_override` (Deferred), classic/TDABC choice, CCR 80% default. Three settings tables, three RLS policies, three update paths. Each obeys AD-3. *Suggested AD-23 candidate:* "There is exactly one `tenant_settings` table keyed on `tenant_id` with a `settings JSONB` column validated against a per-tenant-versioned JSON Schema. Sub-keys: `onboarding` (M0), `baseline` (M1), `abc` (M9), `ai` (M10, AD-7). Migrations of schema are versioned; the `settings_version` column gates which module's writes are accepted. No module creates a parallel settings table."

- **[high] Reporting period alignment (M5 ↔ M8)** — AD-15 pins fiscal-period keys as `'YYYY-MM'`. M8 introduces a "virtual period" (PRD §10) which is *not* a fiscal period. M5's YTD calculation (12개월) does not say whether virtual periods count. M5's engineer excludes virtual periods from YTD. M8's engineer wants the budget-vs-actual diff report (PRD §10 step 4) inside M5's 12-month view. Result: report period boundaries differ. Each obeys AD-6 (no real fiscal period is corrupted), AD-8, AD-15. *Suggested AD-24 candidate:* "Period keys are typed: `'YYYY-MM'` (real fiscal) and `'YYYY-MM#B<n>'` (virtual budget scenario `n`). M5's YTD queries accept a `period_kind` filter that defaults to `'fiscal'`; the budget-vs-actual report is a separate query that explicitly joins `period_kind='fiscal'` to `period_kind='virtual'` via `period_key_prefix='YYYY-MM'`. M8 owns the `virtual` namespace; M5 cannot mint virtual periods."

- **[high] M10 AI insight cache invalidation (M10 ↔ M3 ↔ M11)** — PRD §8.1 M10(b) says "캐시 = 마감 완료 시점부터 다음 마감 시작까지 보존, 마감 데이터 변경 시 폐기." But what invalidates "마감 데이터 변경"? A V4-driven re-allocation before close? A reversal row on a closed period? An input edit by the user? Two engineers can build two different cache-invalidation triggers. M10's engineer invalidates on any `monthly_inputs` write. M3's engineer invalidates only on a new calculation run. M11's engineer invalidates only on close+reopen. Each obeys AD-7. *Suggested AD-25 candidate:* "M10's insight cache is keyed on `(tenant_id, period_key, calculation_result_hash)`. The cache is invalidated on (a) any new AD-4 transaction commit for the same `(tenant_id, period_key)`, (b) any AD-2 reversal row INSERT for the same period, (c) M11's reopen action. The trigger is a single DB row-level notification consumed by M10's adapter — not application-level polling."

- **[medium] is_estimated propagation (M2 ↔ M3 ↔ M5)** — E7 says `is_estimated` badge on inputs. AD-7 says AI outputs are drafts. But PRD §7.1 also says "동인 실적 … AI 추출 + 추정 모드 (`is_estimated` 배지)" — so a single field can be both AI-extracted (AD-7 territory) and estimated (E7 territory). M2's engineer treats `is_estimated=true` as input-ready. M3's engineer treats `is_estimated=true` as a "must be confirmed before calculation" gate (over-applying AD-7). Each obeys AD-7, AD-13. *Suggested AD-26 candidate:* "Two distinct flags: `source ∈ {'manual','excel','ai_extracted','ai_insight'}` (AD-7 enforcement surface) and `is_estimated BOOLEAN` (E7 UI surface). M3's engine gate checks `source='ai_extracted'` (reject) but does *not* check `is_estimated` (allow, badge passes through). M5 displays the badge for `is_estimated=true` rows regardless of source."

- **[medium] Department / cost-center entity (M1 ↔ M3 ↔ M9)** — M1 owns "부서" (PRD §8.1 M1). M3 uses departments for allocation. M9 uses departments for CCR. The ERD does not show a `DEPARTMENT` table. Two engineers can each create one: M1's engineer makes a `departments` table with `name, manager_user_id, is_active`. M9's engineer makes a `cost_centers` table with `name, capacity_hours, is_abc_eligible`. ABC and traditional will reference different identifiers, breaking the AD-21 CCR semantics. Each obeys AD-3, AD-8. *Suggested AD-27 candidate:* "A single `departments` table owned by M1 with columns `department_id, name, manager_user_id, is_active, default_capacity_hours, allocation_role ENUM('trad_only','abc_only','both')`. M3 and M9 both reference `department_id`; neither creates a parallel entity. `is_abc_eligible=true` gates CCR computation."

- **[medium] service_role bypass audit (M12 ↔ AD-3)** — AD-3 says "service_role bypass requires an explicit audit-log row." The spine does not say which fields the row must contain (actor, reason, scope, duration), who is allowed to invoke service_role, or whether operator console (M12) actions are the only allowed scope. M12's engineer writes audit rows with `{actor='operator', reason}` for the 5 documented M12 actions. The next time a developer needs a service_role write (e.g., M11's reversal-by-operator) they ship a different shape. *Suggested AD-28 candidate:* "The `service_role_bypass` audit row is a strict schema: `{bypass_id, tenant_id, requested_action, reason, actor_user_id, scope_tables[], expires_at}`. M12's operator console is the only client that may invoke `service_role`. CI rejects any new client that imports a service-role credential."

- **[medium] M3 result exposure to M5 (AD-4 vs M5 reports)** — AD-4 says "no result is exposed to the client until commit." M5 reports are read after commit, so this is fine. But M5 also wants a "pre-commit preview" (PRD §8.1 M5 requires 21종 보고서, with no clause forbidding pre-commit). M5's engineer can build a preview endpoint that returns the `state='draft'` row. M3's engineer (reading AD-4 strictly) refuses. Each obeys AD-4 (one permits, one forbids the same thing). *Suggested AD-29 candidate:* "Pre-commit preview is allowed only via a separate read port that returns `state='draft'` results with a `PREVIEW` banner and `verification_status='pending'`. The committed-row port and the preview port are different engine adapters; AD-4 governs only the committed port. M5 must explicitly call the preview port and display the banner."

- **[medium] V-row trigger order on multi-segment tenants (M3 ↔ M6)** — AD-12 says V1·V4·V7·V8 fire in that order. PRD §11 V4 is "제조원가↔매출원가↔재고 차이 4요소 분해" (traditional-only). V7 is "ABC 무결성." For ③ tenants, two engineers can each pick: V1→V4→V7→V8 (PRD literal), or V1+V4 (traditional) then V7 (ABC) then V8 (regression). Both orders satisfy AD-12. The order changes the partial-failure mode: V4 failure on traditional blocks V7; the alternative lets ABC compute against a broken traditional base. *Suggested AD-30 candidate:* "V-row execution order is fixed: V1 → V4 → V7 → V8 for all tenant kinds. Any V-row failure aborts subsequent verifications in the same AD-4 transaction; no partial-result commit is allowed. M3's orchestrator exposes this sequence as a single port; M6 cannot re-order. For ② (service-only) tenants, V1 and V4 are skipped (no traditional path), and V7/V8 still run."

- **[medium] M2 input mode keying (M2 ↔ M3)** — E1 says "월합계 기본 + 일자별 선택." M2's engineer stores 일자별 inputs as separate rows with `record_date`. M3's engine adapter normalizes them per AD-13. But the adapter does not say whether the engine's `MonthlyInput` always uses month-totals or whether the daily rows are addressable from reports (PRD §9 #12 재고 수불부 might want daily granularity for some). M2's engineer keeps `record_date`; M5's engineer wants it dropped post-calculation. Each obeys AD-13. *Suggested AD-31 candidate:* "M2's `daily_inputs` (일자별 모드) is append-only (AD-2) and persists for the fiscal year + 1 (UJ-1 retention). AD-13's `MonthlyInputAdapter` is the only reader; engine sees month-totals only. M5 reports do not read `daily_inputs` directly."

- **[low] M0 onboarding vs M1 baseline ordering** — M0 includes "회계연도 시작월" and M1 includes "BOM." AD-6 ties fiscal-period close, but the spine does not pin the user-flow ordering (must M0 complete before M1 accepts data?). M0's engineer allows BOM creation during onboarding. M1's engineer blocks BOM until M0's fiscal year is set. Each obeys AD-3, AD-6, AD-13. *Suggested AD-32 candidate:* "M0's `(fiscal_year_start_month, currency, language, industry)` must be set before M1 accepts any BOM row. Enforced by M1's write-side check; not a UI-only gate. M2's adapter does not re-check."

- **[low] M0 settings (currency, language) and M5 report rendering** — AD-8 says display format is per currency. M5's report PDF generator caches templates. M0's engineer changes currency at M0. M5's engineer ships currency-cached templates. Each obeys AD-3, AD-8. The PDF template cache invalidation is the gap. *Suggested AD-33 candidate:* "M5 report templates are re-rendered on every request, not cached. If caching is later introduced, the cache key must include `(tenant_id, currency, language, period_kind, template_version)`."

- **[low] Engine port vs engine adapter boundary for AI extraction (M0 ↔ M10)** — AD-1 forbids `engine → adapters` but allows `api → adapters` for input drafts. M0's engineer writes AI extraction through the `db` adapter (allowed). M10's engineer writes AI extraction through a new `ai_extraction` adapter (also allowed). Two writers, one logical data store. *Suggested AD-34 candidate:* "AI extraction is a single outbound port `DocumentExtractionPort` with one adapter `claude_vision` under `packages/cost_engine/adapters/ai/`. M0 calls it; M10 calls it; no other adapter may be created."

- **[low] M8 budget scenario vs M3 calculation invariants** — M8 forces `max_scenarios=1` (Deferred). M3's engine accepts a `period_key`. M8's engineer wants a "compare scenarios" feature; M3's engineer refuses because the invariant says one scenario. The divergence: the AD does not say who owns the "one scenario" rule. *Suggested AD-35 candidate:* "M8 owns the `max_scenarios=1` enforcement. M3's calculation accepts a `scenario_id` parameter; if `null`, the real period is computed; if non-null, the engine does *not* write to `fiscal_period_snapshots` (M5 reads from a separate `virtual_snapshots` table owned by M8)."

## What Holds Up

The following ADs genuinely close a real divergence surface and should not be relaxed:

- **AD-1 (Modular Monolith + Hexagonal Core)** — Engine purity is the spine's strongest pillar; import-linter enforcement is correctly named and prevents the most catastrophic class of cross-layer shortcut.
- **AD-2 (Append-only ledger)** — Trigger-level enforcement of INSERT-only is concrete and leaves no room for engineer divergence on mutation policy.
- **AD-3 (Multi-tenant RLS)** — `tenant_id` derivation from JWT (not request body) is the right rule; the gap is bypass audit (AD-28 candidate), not the policy itself.
- **AD-4 (Calculation atomicity)** — REPEATABLE READ + in-transaction verifications prevents the partial-result class. The gap (AD-20, AD-29 candidates) is the *state machine* around the committed row, not the transaction itself.
- **AD-5 (Engine purity)** — `f(inputs) -> outputs` is unambiguous; the enforcement surface (lint) is named.
- **AD-6 (Fiscal-period close lock)** — Trigger on `status='closed'` is concrete. The gap (AD-22 candidate) is the *reversal-row construction*, not the lock.
- **AD-7 (AI non-authoritative)** — The `input_drafts` boundary is real. The gap (AD-17, AD-26 candidates) is the *promotion step* and the *interaction with `is_estimated`*, not the boundary itself.
- **AD-8 (Monetary types)** — `BIGINT` for KRW and `NUMERIC(18,2)` for USD plus `Decimal` in Python leaves no room for engineer divergence on the type. Display formatting is correctly pushed to the UI layer.
- **AD-9 (Data residency = KR region)** — Region pinning is concrete and unambiguous.
- **AD-10 (Identity & roles)** — Four roles + JWT claims are explicit. The gap is the `consultant_proxy` flow's exact API surface, not the role list.
- **AD-11 (Dependency direction)** — `ui → api → services → ports → engine` is concrete; import-linter is named.
- **AD-14 (Stack pinned)** — Version pinning with ban-list is concrete.
- **AD-15 (Conventions)** — Naming, date/time, IDs, error envelope, logging, money are all explicitly enumerated.

## Summary

The 15 ADs form a sound substrate for *module-internal* contracts. The 22 candidate ADs (AD-16 through AD-35, plus AD-36/AD-37 for the supplementary coverage) are all about *cross-module shared data shapes* (snapshots, cost objects, departments, periods, settings) and *cross-module state machines* (promotion, reversal, cache invalidation, snapshot state, V-row order). The deepest gaps are:

1. **Snapshot shape and state** (AD-16, AD-20) — every module touches this; missing schema is the highest-leverage hole.
2. **AI draft → confirmed input promotion** (AD-17) — the most likely source of "AI contamination" in practice.
3. **Cost-object identity** (AD-18) — without this, ③·④ tenants will never reconcile.
4. **Settings topology** (AD-23) — three modules owning three settings tables is the canonical "two owners of one entity" failure.

Closing AD-16 through AD-30 would bring the spine from "has-gaps" to "tight."
